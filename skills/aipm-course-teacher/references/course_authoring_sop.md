# AI PM 课程生成 SOP

创建、扩展、审计或打包 AI 产品经理课程时使用。

这套 SOP 基于第一门课程 `harness` 的生成流程沉淀而来。

## 文件归属

课程生成不是某一门具体课程，它属于课程老师技能里的通用参考文件：

```text
references/course_authoring_sop.md
```

具体课程内容放在：

```text
references/courses/<course-id>/course.md
references/courses/<course-id>/manifest.md
```

## 课程创建流程

## 不可妥协的规则

不要凭记忆临时编一个短目录，就把它叫作新课程。

真正的课程必须通过本 SOP 生成，并且严肃程度要接近内置的 `harness` 课程：有来源、有深入解释、有项目导向、能用于面试准备，也适合反复带学。

如果智能体无法访问可靠来源、用户上传资料或已有笔记，就必须停在资料计划阶段。不能编造官方来源，不能假装读过资料，也不能注册低可信课程。

如果用户说“开一门新课”“学习一门新的课程”“我想学 X”，第一轮回复禁止直接讲课。必须先说清楚：当前还没有这门课的 `course.md`，需要先生成课件、做质量检查、注册为 draft/active，然后才能上课。

禁止把课程只生成到临时 `outputs/` 目录后就开始上课。标准课程必须进入本技能的课程目录：

```text
references/courses/<course-id>/course.md
references/courses/<course-id>/manifest.md
```

课程注册必须写入正在使用的技能目录。如果当前环境只能写工作区，必须向用户申请技能目录写入权限；没有权限时，不要把工作区文件说成已注册课程。

标准课接近 Harness 规模，通常会消耗较多时间和 token。开始生成前必须提醒用户这一点。

## 必须执行的生成阶段

当用户说“生成课程”“做一门课”“新建课程”“我想学 X”等类似请求时，按顺序执行以下阶段：

1. **课程需求确认**：确认主题、学习者水平、目标岗位、期望结果，以及课程是为了学习、面试、项目，还是三者都要。
2. **资料计划**：列出需要的官方文档、技术博客、GitHub 仓库、论文或用户上传资料。如果当前来源不足，要请求联网/资料权限，或先产出资料获取计划。
3. **课程蓝图**：在写完整课件前，先写章节地图、学习阶梯、项目路径、面试路径和预期产物。
4. **完整课件起草**：写真正的 `course.md`，不能只写目录。
5. **来源消化**：把重要链接转成解释、PM 要点、面试表达、产品/项目启发。
6. **质量检查**：运行 `scripts/check_course_quality.py --course <course-id>`；如果脚本不可用，就手动执行同等检查。
7. **课程注册**：质量检查通过前只能注册为 `draft`；通过后才能标记为 `active`。

停止条件：

- 如果无法收集来源，停止在完整起草之前。
- 如果课程缺少来源消化、练习、面试答案、项目路径或来源审计，不要注册为正式课程。
- 如果课程明显比 `harness` 薄，标记为 `draft`，并明确告诉用户缺什么。
- 如果还没有写入 `references/courses/<course-id>/course.md`，不要说“课程已经补好了”。
- 如果没有运行质量检查，不要说“可以正式上课”。

## 新课请求的第一轮回复模板

当用户说“我想学习写 Skill”“开一门新课”这类请求时，第一轮回复必须像这样：

```text
可以，这会作为一门新课程处理。现在还不能直接上课，因为课程库里还没有 `<课程名>` 的课件。

标准课会接近 Harness 课件规模，会消耗较多时间和 token。

我会先按课程生成 SOP 做三件事：
1. 明确课程边界和学习目标。
2. 收集/确认可靠来源。
3. 直接写入技能目录里的 `course.md` 和 `manifest.md`，通过质量检查后再注册为 draft/active。

我先开始做课程蓝图和资料计划。
```

不能在这轮回复里讲“第一节先说人话”。那是在课件生成之后的上课环节。

### 1. 明确课程目标

写作前先确认：

- 目标学习者
- 目标岗位
- 当前水平
- 期望结果
- 课程用于学习、面试、项目，还是三者都要

对当前用户的默认假设：

- 学习者：AI PM 实习生
- 目标：达到 DeepSeek 或同类大模型公司候选人的水平
- 风格：对新手友好，但保持严谨
- 输出：企业级 Markdown 课程

### 2. 建立概念边界

讲清楚课程主题是什么、不是什么。

以 Harness 课程为例：

- 不是 Harness.io 这个 DevOps 平台。
- 不是模型训练。
- 不只是 prompt engineering。
- 它是模型外部的一整套能力系统：instructions、skills、tools、context、workflow、runtime、eval、governance、UX。

如果主题容易被误解，每门课都应该有“先纠偏”章节。

### 3. 创建学习阶梯

好课程应该按这个顺序推进：

```text
人话解释 -> 历史发展 -> 基础词汇 -> 系统架构 -> 核心机制 -> 产品判断 -> 面试表达 -> 实战项目
```

不要一上来堆术语。先从用户已有的心智模型开始。

### 4. 收集可靠来源

优先使用一手或高权威来源：

- 官方产品/公司文档
- 官方技术博客
- 标准/协议文档
- 知名 GitHub 仓库
- 研究论文
- 有信誉的项目文档
- 公认技术专家的长文、演讲或工程笔记，只能作为补充观点，不能替代官方事实。

避免把小博客、内容农场、无来源社交帖或搬运摘要当作核心依据。

如果来源时效性重要，需要联网核验。

### 4.1 权威来源硬标准

标准课必须先建立“来源矩阵”，再开始写完整课件。

来源矩阵至少包含：

| 来源类型 | 最低要求 | 示例 |
|---|---:|---|
| 大企业官方文档/技术博客 | 8 个以上 | OpenAI、Anthropic、DeepSeek、Google、Microsoft/GitHub、Meta、AWS、Cloudflare |
| 标准/协议/论文 | 3 个以上 | MCP、Agent Skills、arXiv 论文、W3C/云厂商标准文档 |
| 知名 GitHub 项目 | 6 个以上 | OpenAI、Anthropic、Microsoft、LangChain、LlamaIndex、Dify、E2B、Langfuse 等 |
| 公认技术专家观点 | 可选，1-4 个 | 只用于补充解释，不作为唯一事实依据 |

严禁：

- 用无来源中文平台文章当核心依据。
- 用营销号、搬运号、SEO 内容农场当核心依据。
- 只贴链接，不解释链接里的知识。
- 把技术专家个人判断说成官方结论。
- 把 GitHub 项目列表当成课程内容，必须说明每个项目解决什么问题、属于哪一层、对 PM 有什么启发。

如果当前无法联网或没有用户上传资料，就不能生成标准课。只能先输出“资料获取清单”，列出必须补齐的官方文档、GitHub 项目和论文。

### 5. 把链接转成知识

不要只列链接。

每个重要链接都要提取：

- 来源说了什么
- 为什么重要
- AI PM 应该记住什么
- 对应哪个产品/系统层
- 如何影响面试表达
- 如何转成项目机会

推荐表格：

| 来源 | 有用知识 | PM 要点 | 产品/项目启发 |
|---|---|---|---|

对 GitHub 项目，至少要消化：

- 项目解决什么问题。
- 它属于课程主题里的哪一层。
- 它的核心抽象或架构是什么。
- 它适合什么场景，不适合什么场景。
- AI PM 能从它学到什么产品判断。
- 是否能转化成 DeepSeek 或目标公司的产品机会。

### 6. 编写核心课程

推荐课程结构：

1. 纠偏 / 范围
2. 一页纸总览
3. 为什么这个主题对 AI PM 重要
4. 术语表
5. 标准架构或框架
6. 历史前因后果
7. 什么算 / 什么不算
8. 项目生态
9. 核心机制
10. 评估和治理
11. PRD 模板
12. 目标公司产品机会
13. 面试问答
14. 实战练习
15. 来源知识库
16. 来源审计
17. 最终总结

企业级课程的最低结构：

- 新手纠偏：这个主题是什么、不是什么。
- 一页纸总览：给一个好记的心智模型。
- 历史前因后果：为什么这个主题会出现。
- 面向新手的术语表。
- 架构 / 框架章节。
- 带具体例子的核心机制。
- 产品经理判断框架。
- 目标公司或目标岗位场景。
- 项目生态或相关工具/项目。
- PRD / 产品机会章节。
- 评估、指标、风险、治理和体验。
- 面试问答：包含强回答和追问陷阱。
- 实战练习和课后任务。
- 来源知识库：把链接消化成有用知识。
- 来源审计和观点分级。

### 7. 添加视觉材料

对纯文字难以理解的概念，使用视觉材料。

可用视觉类型：

- 生成式概念插图
- Mermaid 图
- SVG/PNG 信息图
- 路线图
- 飞轮图
- 对比矩阵

重要打包规则：

- 带本地图片路径的 Markdown 在飞书或网页编辑器中可能失效。
- 如果要导入飞书，优先考虑 Word 导入；只有平台支持时才考虑单文件/base64 Markdown。
- 普通 Markdown 要把图片放在相邻文件夹，并验证引用路径。

### 8. 添加项目路径

每门 AI PM 课程最终都应该导向一个项目。

项目路径应包含：

- 目标用户
- 痛点
- 产品目标
- 核心工作流
- 系统分层
- MVP 范围
- 指标
- 风险
- 评估方案
- 面试表达

### 9. 添加练习和面试训练

包含：

- 概念解释练习
- 产品拆解练习
- PRD 写作练习
- 评估数据集练习
- 模拟面试问题
- 追问陷阱

学习者应该能讲出来，而不是只会读。

### 10. 审计来源

添加来源审计章节：

- 按权威性给来源分级
- 区分官方事实和课程解释
- 把产品判断标记为课程归纳
- 说明没有使用哪些来源
- 列出弱假设和不确定性

这样可以避免课程看起来像没有来源的 AIGC。

质量底线：

- 技术类标准课必须至少包含 80 个来源链接。
- 技术类标准课必须至少包含 40 个大企业官方/标准/论文来源。
- 技术类标准课必须至少包含 30 个 GitHub 项目链接。
- 必须有“企业级知识库 / 来源知识库”章节。
- 必须有“重要链接精读”章节，把链接里的知识搬进课程。
- 必须有“来源审计与观点分级”章节。
- 只有相关时才加入知名 GitHub 项目，并说明它们能教会什么。
- 区分事实和课程归纳。
- 产品策略建议要标注为课程归纳，不能说成官方结论。

深度底线：

- 标准课的目标必须接近 `harness` 的严肃程度，完整第一版通常至少应达到 80,000 字符。
- 企业级标准课应尽量接近或超过原 Harness 课件规模，并包含完整来源精读、项目地图、练习、面试、来源审计。
- 狭窄主题的小课可以更短，但必须在 manifest 和课程目录里明确标注为 `mini-course`，并且不能伪装成标准课。
- 课程不能只是目录、链接列表或泛泛文章。

### 11. 注册课程

添加新课程时：

1. 创建 `references/courses/<course-id>/`。
2. 添加 `course.md`。
3. 添加 `manifest.md`。
4. 更新 `references/course_catalog.md`。
5. 如有需要，在 `references/courses/<course-id>/assets/` 下添加资源文件。

注册规则：

- 不完整、过薄、缺少来源或未验证的课程只能是 `draft`。
- 标准课只有通过 `scripts/check_course_quality.py --course <course-id> --level standard` 后才能标记为 `active`。
- 小课只有在用户明确要求 mini-course，并通过 `scripts/check_course_quality.py --course <course-id> --level mini` 后，才能标记为 `active`。
- 永远不要把 TODO 占位课程标记为 active。

`manifest.md` 应包含：

- 课程名称
- 适合人群
- 教学目标
- 推荐起点
- 项目路径

### 12. 验证课程

交付前检查：

- 检查文件存在。
- 检查图片存在。
- 检查标题层级一致。
- 检查来源链接存在。
- 检查来源审计存在。
- 检查课程目录指向正确文件。
- 如果导出，检查导出文件能打开，且图片能正常展示。
- 可用时运行 `python scripts/check_course_quality.py --course <course-id> --level standard`。
- 如果质量检查失败，必须先修课程，再注册或宣称完成。

## 课程更新流程

当用户要求改进已有课程时：

1. 识别用户不满点。
2. 定位受影响的课程章节。
3. 补充缺失的知识、例子、视觉材料或来源消化。
4. 除非用户要求新版本，否则保留原课程路径。
5. 重新执行验证。
6. 如果范围变化，更新 `manifest.md`。

常见问题和修复方式：

| 用户反馈 | 修复方式 |
|---|---|
| “只有链接” | 增加来源精读和 PM 要点 |
| “太抽象” | 增加人话解释和具体例子 |
| “不够图文并茂” | 增加图片、图表和视觉总结 |
| “没有前因后果” | 增加历史因果章节 |
| “不适合上课” | 增加上课流程、练习和小测 |
| “不能在飞书打开” | 提供适合 Word 导入或图片友好的 Markdown |

## 教学集成

课程创建后，课程老师应当：

1. 确认课程文件已经写入技能目录。
2. 加入课程目录。
3. 创建每日学习状态文件。
4. 询问用户是否从推荐起点开始。
5. 使用通用上课 SOP 上课。

## GitHub 打包 / 跨智能体发布

当用户想公开分享课程老师技能、安装到另一台机器，或适配 Claude Code 等其他编码助手时使用。

将技能打包成一个文件夹：

```text
aipm-course-teacher/
├── SKILL.md
├── references/
├── scripts/
└── state/
```

发布检查清单：

- 保持 `SKILL.md` 平台中立：描述教学行为，而不是某一家产品界面。
- 常见安装位置只能作为示例提到，例如 `~/.codex/skills/` 和 `~/.claude/skills/`。
- 脚本必须通过脚本自身位置推导技能根目录，保持相对路径。
- 不要包含个人每日学习记录、聊天总结、本地截图、导出的私人文档或机器专属绝对路径。
- 保留 `state/daily/.gitkeep` 和 `state/summaries/.gitkeep`，保证克隆后目录结构存在。
- 发布前用 `--help` 或无副作用的只读命令验证脚本。
- 课程目录只能依赖打包进去的课程文件夹。
- 不同运行环境的工具名可以不同：某个助手可能用不同方式调用命令行/搜索工具，但 SOP 本身不变。

如果适配 Claude Code，常见安装路径通常是：

```text
~/.claude/skills/aipm-course-teacher/
```

如果适配 Codex，使用该 Codex 环境配置的技能目录，常见路径是：

```text
~/.codex/skills/aipm-course-teacher/
```

面向用户的上课行为不应因平台不同而改变。
